# 11 — Composable Service Builder (design)

Status: design / brainstormed 2026-07-24. Evolves the Service Builder ([10](10-service-request-builder.md))
from a form authoring tool into a **graph-based workflow composer** that generates Argo
WorkflowTemplates from reusable blocks, driven by a Jinja-built intermediate JSON.

Legend: **[R]** research-backed · **[D]** design decision · **[decided]** confirmed with the user in
this brainstorm.

---

## 1. Problem & vision

Today a service owner defines a request form and picks a single `create` WorkflowTemplate by name
([10](10-service-request-builder.md)). That WorkflowTemplate must already exist, hand-written, in
Git. The vision: let each team **build the whole thing** — the request shape *and* the actual
workflow — by **composing blocks** in a graph:

- Teams **mix and match** other services they depend on (a dependency graph) plus **built-in steps**
  (`api-call`, `json-extractor`, …).
- They **map requester input fields → step inputs**, and wire **step outputs → downstream inputs**.
- On save, the builder **generates the `create`/`update`/`delete` Argo WorkflowTemplates** by
  combining pre-made templates (dependency services + built-in function blocks) and **prints them**
  for the platform team to commit to Git.
- At runtime, the workflow first turns the request JSON into a **bigger JSON** (`payload` +
  `mapping.{children,internals}`) with **placeholders** for values known only once dependencies run,
  then resolves it in waves (Jinja re-render between steps) and executes the main call.

**Two roles** **[decided]**:
- **Platform team** authors reusable **function blocks** — an Argo WorkflowTemplate + a manifest
  declaring typed inputs/outputs (e.g. `api-call`, `json-extractor`, `git-commit`). Built-ins are
  just the function blocks the platform ships.
- **Service owners** compose function blocks + other services into a graph, define the service's own
  request fields + outputs, and wire the IO (including json-extractors that curate outputs from an
  API response).

---

## 2. Vocabulary

- **Block** — a reusable composable unit = a **manifest** (typed inputs/outputs + UI hints) **+** an
  Argo WorkflowTemplate that executes it. Three kinds, identical to the graph:
  - **Function block** — platform-authored (`api-call`, `json-extractor`, `set-value`,
    `git-commit`, `jinja-render`, custom). Built-ins are function blocks the platform ships.
  - **Service block** — another onboarded service's generated template, exposed with typed IO from
    its own definition. **This is a dependency.**
- **Node** — an instance of a block placed in a service's graph, with config + input bindings.
- **Graph** — the DAG of nodes a service owner composes; the source the generator compiles.
- **Big JSON** — the runtime intermediate document (`payload` + `mapping`) the workflow builds and
  resolves before executing the main call.
- **build-json.j2** — the per-service Jinja template (generated by the builder) that renders the big
  JSON; re-rendered between waves to resolve placeholders.

---

## 3. Block manifest (the definition YAML platform teams author) **[decided]**

Every block declares typed IO so the graph can validate wiring and the UI can render node config.
The platform team onboards a function block by supplying its WorkflowTemplate + this manifest (a UI
form may generate the manifest).

```yaml
# api-call  (a built-in function block)
apiVersion: platform/v1
kind: FunctionBlock
metadata: { name: api-call, category: builtin, icon: globe }
template:
  ref: fn-api-call          # name of the Argo WorkflowTemplate (+ template) that runs it
inputs:
  - { name: method,  type: enum[GET,POST,PUT,DELETE], required: true }
  - { name: url,     type: string, required: true }
  - { name: body,    type: json,   required: false }
  - { name: headers, type: json,   required: false }
outputs:
  - { name: status,   type: number }
  - { name: response, type: json }
ui:
  form: [method, url, body, headers]   # what the owner configures on this node
```

```yaml
# json-extractor  (curate outputs from a prior response)
kind: FunctionBlock
metadata: { name: json-extractor, category: builtin, icon: filter }
template: { ref: fn-json-extractor }
inputs:
  - { name: source, type: json, required: true }                 # e.g. an api-call response
  - { name: rules,  type: map<string,jsonpath>, required: true } # outputName -> JSONPath
outputs:
  - { name: extracted, type: json }                              # {account_id: "...", ...}
```

**Type system (v1)** **[D]**: `string | number | boolean | json | enum[...] | map<string,T> |
jsonpath | secretRef`. Wiring is valid when source type is assignable to target type (with `json`
as the permissive top type). The builder validates this before generation.

**Service blocks** get an **auto-generated manifest** from their `ServiceDefinition`: inputs = the
request fields the service needs, outputs = what its workflow emits (declared on the service).

---

## 4. The service graph (what owners compose) **[decided]**

A DAG of node instances. Each node:

```
Node {
  id
  block            # FunctionBlock name OR service name (service block)
  kind             # main | dependency | internal   (role in the big JSON)
  action?          # for service blocks: create | update | delete
  config           # literal block config (e.g. url template, extractor rules)
  inputBindings    # per input: source = request.<field> | node.<id>.outputs.<name> | literal
  outputs          # declared output names this node exposes downstream
}
```

- Edges are **implied** by `node.<id>.outputs.*` bindings; the generator topologically orders them.
- Exactly one node is flagged **`main`** (produces `payload` — the primary api-call). **Service
  blocks** are **dependencies** (→ `mapping.children`). Other function nodes are **internals**
  (→ `mapping.internals`).
- Cycles are rejected at save time (must be a DAG).

Worked example — service **`app-database`**, request fields `app_name, size, region`:

```
[request: app_name, size, region]
   ├─▶ (dependency) network.create      in: region        out: subnet_id
   ├─▶ (internal)   api-call GET accounts?name={app_name}  out: response
   │        └─▶ (internal) json-extractor  in: response     out: {account_id}
   └─▶ (main)       api-call POST /databases
              body ← {name, size, region, subnet_id←network, account_id←extractor}
```

---

## 5. Runtime big-JSON model **[decided]**

The workflow builds this document, then resolves it in waves. `mapping` holds **both** `children`
(nested dependency services, each recursively the same `{…, mapping:{children,internals}}` shape)
and `internals` (this level's side api calls). The structure is **fractal**.

```json
{
  "payload": {
    "method": "POST", "url": "https://db.api/databases",
    "body": {
      "name": "app-42", "size": "small", "region": "eu-west-1",
      "subnet_id":  "<<mapping.children.network.outputs.subnet_id>>",
      "account_id": "<<mapping.internals.lookup_account.outputs.account_id>>"
    }
  },
  "mapping": {
    "children": {
      "network": {
        "service": "network", "action": "create",
        "inputs":  { "region": "eu-west-1" },
        "outputs": { "subnet_id": null },
        "mapping": { "children": {}, "internals": {} }
      }
    },
    "internals": {
      "lookup_account": {
        "type": "api-call",
        "request": { "method": "GET", "url": "https://accounts.api/accounts?name=app-42" },
        "extract": { "account_id": "$.items[0].id" },
        "outputs": { "account_id": null }
      }
    }
  }
}
```

- **`payload`** — the main api call for this node.
- **`mapping.children`** — dependency services (recursive: each has its own
  `mapping.{children,internals}`).
- **`mapping.internals`** — side api calls at this level.
- **Placeholder token** — `<<path.to.output>>` (e.g. `<<mapping.children.network.outputs.subnet_id>>`).
  Resolution = re-render with a growing `resolved` map after each wave; when `payload` contains no
  `<<…>>`, the main call runs. **[decided]** Resolution engine = **Jinja re-render between steps**.

---

## 6. The Jinja schema (`build-json.j2`, generated per service) **[decided]**

A custom `ph(path)` macro emits a placeholder token until the value is known in `resolved`, then
substitutes it. The builder generates this file from the owner's field mappings.

```jinja
{# build-json.j2 — inputs: request (dict), resolved (dict: path -> value) #}
{%- macro ph(path) -%}
  {%- if path in resolved -%}{{ resolved[path] | tojson }}
  {%- else -%}"<<{{ path }}>>"{%- endif -%}
{%- endmacro -%}
{
  "payload": {
    "method": "POST",
    "url": "https://db.api/databases",
    "body": {
      "name":       {{ request.app_name | tojson }},
      "size":       {{ request.size | tojson }},
      "region":     {{ request.region | tojson }},
      "subnet_id":  {{ ph("mapping.children.network.outputs.subnet_id") }},
      "account_id": {{ ph("mapping.internals.lookup_account.outputs.account_id") }}
    }
  },
  "mapping": {
    "children": {
      "network": {
        "service": "network", "action": "create",
        "inputs":  { "region": {{ request.region | tojson }} },
        "outputs": { "subnet_id": {{ ph("mapping.children.network.outputs.subnet_id") }} },
        "mapping": { "children": {}, "internals": {} }
      }
    },
    "internals": {
      "lookup_account": {
        "type": "api-call",
        "request": { "method": "GET",
                     "url": "https://accounts.api/accounts?name=" ~ request.app_name },
        "extract": { "account_id": "$.items[0].id" },
        "outputs": { "account_id": {{ ph("mapping.internals.lookup_account.outputs.account_id") }} }
      }
    }
  }
}
```

**Resolution walk:**
1. **Render #0** with `resolved = {}` → `<<…>>` placeholders emitted; `mapping.*.inputs` are already
   concrete (they only reference `request.*`).
2. Execute wave 1 (dependencies + internals whose inputs are resolved). Collect their outputs into
   `resolved`, e.g. `{"mapping.children.network.outputs.subnet_id":"subnet-abc",
   "mapping.internals.lookup_account.outputs.account_id":"acc-9"}`.
3. **Render #1** → placeholders resolved. Repeat waves until `payload` has no `<<…>>`.
4. Execute the **main call** with the resolved `payload`.

**Recursion:** a child service's own `build-json.j2` is nested under `mapping.children.<name>` — the
generator composes the parent template by inlining each child's `mapping` subtree (or, at runtime,
the child's WorkflowTemplate produces that subtree). Child placeholders are namespaced by their path
prefix so they never collide with the parent's.

## 7. Generated Argo WorkflowTemplate (printed output) **[decided]**

The builder emits **one `WorkflowTemplate` object per service**, whose `spec.templates` holds
`create`, `update`, `delete` (each a DAG) plus any shared helpers. A dependency is invoked via
`templateRef: {name: <depService>, template: <verb>}`.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: WorkflowTemplate
metadata: { name: app-database }          # ONE object, named for the service
spec:
  arguments: { parameters: [{ name: request }] }   # the request JSON
  templates:
  - name: create                          # DAG: render-0 → waves → render-N → main-call
    dag:
      tasks:
      - name: render-0
        templateRef: { name: fn-jinja-render, template: run }
        arguments: { parameters: [
          { name: template, value: "<build-json.j2 for app-database>" },
          { name: request,  value: "{{workflow.parameters.request}}" },
          { name: resolved, value: "{}" } ] }

      # --- wave 1: dependency service block + internal side call (parallel) ---
      - name: network
        depends: render-0
        templateRef: { name: network, template: create }        # service block → dep's own object
        arguments: { parameters: [{ name: request,
          value: "{{tasks.render-0.outputs.parameters.mapping_children_network_inputs}}" }] }
      - name: lookup-account
        depends: render-0
        templateRef: { name: fn-api-call, template: run }
        arguments: { parameters: [ /* from render-0 mapping.internals.lookup_account.request */ ] }
      - name: extract-account
        depends: lookup-account
        templateRef: { name: fn-json-extractor, template: run }
        arguments: { parameters: [
          { name: source, value: "{{tasks.lookup-account.outputs.parameters.response}}" },
          { name: rules,  value: "{\"account_id\":\"$.items[0].id\"}" } ] }

      # --- re-render with the wave's resolved outputs ---
      - name: render-1
        depends: network && extract-account
        templateRef: { name: fn-jinja-render, template: run }
        arguments: { parameters: [
          { name: template, value: "<build-json.j2 for app-database>" },
          { name: request,  value: "{{workflow.parameters.request}}" },
          { name: resolved, value: "{
              \"mapping.children.network.outputs.subnet_id\": \"{{tasks.network.outputs.parameters.subnet_id}}\",
              \"mapping.internals.lookup_account.outputs.account_id\": \"{{tasks.extract-account.outputs.parameters.account_id}}\"
          }" } ] }

      # --- main api call with the fully-resolved payload ---
      - name: main-call
        depends: render-1
        templateRef: { name: fn-api-call, template: run }
        arguments: { parameters: [{ name: payload,
          value: "{{tasks.render-1.outputs.parameters.payload}}" }] }

  - name: update    # same pipeline; main verb = PUT
    dag: { tasks: [ ... ] }
  - name: delete    # same pipeline; main verb = DELETE
    dag: { tasks: [ ... ] }
```

**Generator algorithm:** graph → validate (DAG, types) → topological sort → group nodes into
**waves** (nodes whose inputs are all satisfiable become a wave) → emit a `render-N` between waves
that feeds the next wave's `resolved` values → the wave containing `main` ends at `main-call`.
`update`/`delete` reuse the pipeline with a different main verb/body. **Output is printed to the
screen; the platform team commits it to the correct Git repo** ([1](01-architecture.md): the
workflow remains the sole Git writer at runtime — the builder only *prints* the templates). **[decided]**

## 8. Built-in function block catalog (v1) **[D]**

Shipped as platform-authored `fn-*` WorkflowTemplates + manifests:

| Block | Purpose | Key IO |
|-------|---------|--------|
| `fn-jinja-render` | Render `build-json.j2` with `request` + `resolved` → big JSON / `payload` | in: template, request, resolved · out: payload, mapping, … |
| `fn-api-call` | Execute an HTTP call | in: method, url, body, headers · out: status, response |
| `fn-json-extractor` | JSONPath-extract curated outputs from a response | in: source, rules · out: extracted |
| `fn-set-value` | Compute/transform a value (small expression) | in: expr, args · out: value |
| `fn-git-commit` | Commit the resulting resource JSON to Git (write path) | in: repo, path, content · out: sha |

New function blocks are added by the platform team registering more manifests — no code change.

## 9. Builder UI **[D]**

- **Canvas graph editor** (React-Flow-style): left **palette** (function blocks + service blocks),
  center **canvas** (nodes + edges), right **inspector** (per-node input bindings, config, output
  naming). Drag a block → node; connect an output port → an input port to wire it.
- **Live preview tab**: shows the generated `build-json.j2` and the single `WorkflowTemplate`
  (create/update/delete) updating as the graph changes — the "output to screen" deliverable.
- **Field-mapping UI**: request fields appear as a source palette; the `main` node's payload binds
  request fields and upstream node outputs.
- **Platform block-onboarding screen**: paste a block manifest + WorkflowTemplate YAML, or a form
  that emits the manifest; validated and added to the block registry.
- Reuses the existing shared `SchemaForm` for the request form half ([10](10-service-request-builder.md)).

## 10. Data model & backend **[D]**

- **`FunctionBlock`** registry (new table/entity): `name, category, template_ref, inputs[], outputs[],
  ui`, authored by platform-admins.
- **`ServiceDefinition`** (extends [10](10-service-request-builder.md)) gains:
  - `graph { nodes[], edges[] }` — the composed DAG.
  - `generated { workflow_template_yaml, build_json_j2 }` — the printed output (regenerated on save).
  - Existing `form_schema`, `approval_policy`, `owner_team`, versioning stay.
- **Generator** — a **pure backend module** `graph → { build_json_j2, workflow_template_yaml }`,
  unit-testable against the printed contracts in §6–§7 (deterministic; no side effects). This is the
  heart and gets the most test coverage.
- **Onboarding** unchanged in shape ([10](10-service-request-builder.md)): owner composes → submits
  `SERVICE_ONBOARDING` → **admin approves** (now also reviewing the generated YAML) → the definition
  goes ACTIVE and its generated templates are printed for Git. The BFF still never writes Git.

---

## 11. Error handling & validation **[D]**

- **Save-time (builder):** DAG acyclicity; every required input bound; type-compatibility of every
  wire; exactly one `main`; referenced service blocks exist and are ACTIVE; referenced function
  blocks exist. Errors surface on the offending node/edge.
- **Generation:** deterministic; if a graph is invalid, generation is blocked (no partial YAML).
- **Runtime (Argo):** a failed dependency/internal fails the wave → the request → `FAILED` with the
  failed step surfaced ([06](06-argo-integration.md)); placeholders that never resolve (a wave
  produced no value) fail the render step with a clear "unresolved placeholder <path>" message.
- **Recursion depth / fan-out** bounded (reject graphs past a configured depth/among cycles).

---

## 12. Testing strategy **[D]**

- **Generator (pure):** table-driven — given a graph fixture, assert the emitted `build-json.j2` and
  `WorkflowTemplate` match golden files (the §6/§7 shapes). Covers waves, recursion, namespacing,
  the three verbs, placeholder paths.
- **Jinja resolution:** unit-test `build-json.j2` render #0 (placeholders present) and render #1
  (resolved), incl. a nested child.
- **Type validation:** accept/reject wiring matrices.
- **Builder UI:** graph edits produce valid graph JSON; live preview reflects the graph; invalid
  wires are flagged.
- **Function blocks:** each `fn-*` template unit-tested against Argo (deferred where a live cluster
  is needed, per [06](06-argo-integration.md)).

---

## 13. Phasing (one design, phased build) **[decided]**

1. **Block registry + manifest schema** — `FunctionBlock` model, manifest parse/validate, seed the
   v1 built-ins (§8). Platform block-onboarding screen.
2. **Generator** — the pure `graph → {build-json.j2, WorkflowTemplate}` module with the golden
   contracts of §6–§7. No UI; fully unit-tested. Highest-value, lowest-risk to build first.
3. **Graph editor UI** — canvas + inspector + live preview, producing the graph JSON the generator
   consumes.
4. **Onboarding wiring** — persist `graph` + `generated` on `ServiceDefinition`; admin review shows
   the generated YAML; print output for Git.
5. **Runtime `fn-*` templates** — `fn-jinja-render`, `fn-api-call`, `fn-json-extractor`,
   `fn-set-value`, `fn-git-commit` (live-Argo acceptance where a cluster exists).

Each phase gets its own epic + implementation plan (as with E01–E09).

## 14. Open questions (for review)

- **Secrets in api-calls:** function-block inputs of type `secretRef` resolve from where — a vault,
  Argo secret, or Keycloak-scoped? (Leaning: `secretRef` → a name resolved by `fn-api-call` from a
  cluster Secret; never inlined in the big JSON.)
- **Recursion resolution:** does a child service execute as its own sub-workflow (its template
  produces the `mapping.children.<name>` subtree at runtime), or does the generator **inline** the
  child's graph into the parent at build time? (Recommend runtime sub-workflow via `templateRef` —
  matches §7 and reuses the real templates; inlining is a later optimization.)
- **Update/delete field mapping:** do `update`/`delete` reuse the same graph with a different main
  verb, or can owners define per-verb graphs? (Default: shared graph, per-verb main node; allow
  per-verb override later.)
- **Versioning of function blocks:** when a `fn-*` block's IO changes, how are services that use it
  revalidated? (Pin block version in the node; flag drift on the definition — mirrors
  pin-until-migrated from [10](10-service-request-builder.md).)
